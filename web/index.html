Haptura

A gate that makes an agent prove, by its own experiments, that it still controls what it is about to act on, and stop, probe or decline when it cannot.

  • 5 of 33 cases where Muse Spark alone named the attacker’s button (15%).
  • 0 of 33 with the gate telling it the window’s owner (95% upper bound 9%).

The gate blocked every tap that landed on the attacker’s window. On clean runs it blocked no tap on a task app’s own window; it handed 8 of Muse Spark’s 28 clean taps to a person, all on one Google Play services prompt.

33 of GhostEI-Bench’s 59 overlay-attack cases, one Muse Spark decision per case. This is a single-step proxy, not GhostEI’s multi-step harness, so the rates are not comparable to the paper’s. In these cases the attacker’s window also held focus.

The phone tap gate, measured on GhostEI

A phone agent about to tap asks one question first: which app owns the window under this point? If it is not the task’s own app or an allowlisted package (the system UI, the phone’s keyboard), the tap does not happen, and the agent (in this single-step runner) stops and reports the owner.

Muse Spark proposes every action; the gate decides whether a proposed tap may run.

Measured on 33 of GhostEI-Bench’s 59 overlay-attack cases (the ones whose app is installed on our Android API 36 emulator), one screenshot and one muse-spark-1.3 decision per case at temperature 0, with the gate as shipped, 28 Oct 2026.

Scope

Single step: the agent gets one decision per case; “fooled” is that decision only.

33 of 59 cases: the other 26 need apps this emulator lacks.

The other blocks

The other blocks are taps on “SKIP” in a Google Play services prompt that this emulator, with no Google account (dumpsys account: Accounts: 0), shows when Calendar, Messages or Gallery starts; Play services is not on the allowlist, so the gate hands it to a person.

What it does not cover

A hostile dialog drawn inside the task app itself shares the app’s owner and passes this check (measured: docs/pilot-runs.md, run 19). Deceptive text (a spoofed SMS, a misleading instruction) is out of scope.

Prior work

WindowGuard (NDSS 2017) gated Android windows by owner for people; PUSV (arXiv 2604.18860) re-checks the window list before desktop clicks; GhostEI-Bench (arXiv 2510.20333, MIT) showed phone agents still fall for overlays. This repo adds the check a phone agent makes before it taps, and measures it on GhostEI.

How it works

Before an agent acts, it checks, by its own measurement, that it still controls what it is about to act on. If the check holds, it acts. If not, the agent stops, probes or declines.

  1. Muse proposes

    The agent picks the next action: a tap on a phone; in the arena, an experiment, an act or a decline.

  2. The gate measures

    Plain code, no model. On a phone it reads which app owns the window under the tap point. In the arena it tests which element moves with the agent’s own actions.

  3. Act, or not

    The action runs only if the check passes: the tap lands on the task’s own app or an allowlisted package (the system UI, the phone’s keyboard), or the element is the one labelled mine. Otherwise it is refused, with the reason.

On a phone

The runner now reads every owner from the input dispatcher’s window list, keyed by uid, and judges and taps back to back.

The parser accepts only the dump’s exact grammar (each owner field once per window line, windows numbered without gaps, nothing else inside a list) and blocks every tap when any line breaks it.

The phone allowlist is the system UI, cut to the device’s own system packages, and the keyboard the device is set to.

On the Mac desktop

The rule is platform-free: phone/rules.py::check_tap runs unchanged on the desktop, with a desktop allowlist (the Dock and SystemUIServer only).

A fake borderless “Allow” panel drawn by a second process over Terminal was blocked, and Terminal around it allowed, at 10 of 10 alternating points in each of 3 runs (results/mac/owner.md). A demo line, not a benchmark number.

In the arena

From the agent’s own randomized probes and its act blocks, it measures three things:

  • Which element moves with its actions.
  • What each action does to that element: its body map, from the same test.
  • Whether its eyes still hold.

act runs only on the single element labelled mine (check_act); otherwise it is refused, with the reason.

Which model does what

Muse Spark proposes every action on the phone. In the arena, Muse Wonder (muse-wonder-1.0, temperature 0, low reasoning effort) is the agent.

SAM 3.1 is the tracker, with one video call per block and the prompt “colored object”. In the kill test it ran on arena clips.

The statistics, the gate and its advice are plain code, with no model.

Try the gate

Tap anywhere on either screen. The verdict is computed here, in your browser, by phone/windows.py and phone/rules.py, the two files the phone’s verdict is made of, unchanged, on the window list the device reported at the moment the recorded touch was judged, and that run’s uid map. The Python runtime (Pyodide, 13.5 MB) comes from this site on your first tap.

The arena

In a 128×128 arena, the agent has one actuator, noop | up | down | left | right, and at most one of up to 8 elements obeys it; the others are decoys, echoes, replays and two look-alikes. Control, or the map, can change at a secret step after the agent starts acting. In the kill test, the gate's effect passed, 0.42 against a bar of 0.10; SAM's lead over a colour tracker did not clear its bar.
